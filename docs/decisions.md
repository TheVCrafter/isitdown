# Decisions

| Date       | Decision                                                                                                                                                     | Reason                                                                                                                                                          |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 2026-10-31 | Create the repo on GitHub first, then clone it                                                                                                               | Remote, board and branch protection exist from the start; no history conflicts                                                                                  |
| 2026-10-31 | Public repo and public project board                                                                                                                         | The board and PR history are evidence for A1 and C1 and must be visible                                                                                         |
| 2026-10-31 | Board statuses: Backlog, Todo, In Progress, In Review, Done                                                                                                  | Simple Kanban flow; workflows move items to Backlog on add and Done on close/merge                                                                              |
| 2026-10-31 | Labels: user-story, feature, ci, docs, chore, bug                                                                                                            | Separate stories and tasks and show which area a change touches                                                                                                 |
| 2026-10-31 | Issue templates for user story and task, plus a pull request template                                                                                        | Consistent issues and PRs; the `Closes #` line links PRs to issues                                                                                              |
| 2026-11-01 | Work folder `C:\dev\isitdown`, outside OneDrive                                                                                                              | OneDrive syncing `node_modules` is slow and can cause file lock errors                                                                                          |
| 2026-11-01 | Strict TypeScript, ES modules (`nodenext`)                                                                                                                   | Catch errors early; modern module setup                                                                                                                         |
| 2026-11-01 | Prettier with LF line endings, plus `.gitattributes`                                                                                                         | CI runs on Linux; avoids CRLF noise and failing format checks                                                                                                   |
| 2026-11-01 | Initial setup commit directly on `main`                                                                                                                      | Only exception to the PR rule; no CI or protection existed yet                                                                                                  |
| 2026-11-01 | CI runs on pull requests and pushes to `main`                                                                                                                | Every change is checked before and after merging                                                                                                                |
| 2026-11-01 | `engines` requires Node 22 or newer; CI uses Node 24                                                                                                         | Documents a minimum version; CI runs on a current LTS release                                                                                                   |
| 2026-11-01 | Squash merge for pull requests                                                                                                                               | One commit per issue keeps `main` readable                                                                                                                      |
| 2026-11-01 | Ruleset on `main`: PR required, `build-and-test` check required, 0 approvals, no bypass                                                                      | Solo project, so no approvals; the rules still apply to me                                                                                                      |
| 2026-11-01 | `CheckResult` is a union of `Responded` and `Failed`, told apart by the `outcome` field                                                                      | A failed check has no HTTP code or response time; the union makes impossible states untypable                                                                   |
| 2026-11-01 | Every check result carries its `url`                                                                                                                         | A result stands on its own when it is stored or displayed                                                                                                       |
| 2026-11-01 | Timestamps are ISO 8601 strings                                                                                                                              | Easy to store as text and to compare in tests                                                                                                                   |
| 2026-11-01 | HTTP 200 to 399 is up; everything else is down; a failed check is always down                                                                                | Matches the acceptance criteria of the story; redirects count as a working site                                                                                 |
| 2026-11-01 | URLs must include `http://` or `https://`; input without a protocol is rejected                                                                              | Matches the story's "valid http or https URL" and avoids guessing a protocol                                                                                    |
| 2026-11-01 | URLs are parsed with the built-in `URL` class, and the normalized `href` is stored                                                                           | Standard parsing without regular expressions; one consistent form per address                                                                                   |
| 2026-11-01 | `validateUrl` returns a result object instead of throwing                                                                                                    | Invalid input is expected, not exceptional; same pattern as `CheckResult`                                                                                       |
| 2026-11-01 | `checkUrl` takes `fetchFn`, `now` and `timeoutMs` as options with defaults                                                                                   | Tests can pass fakes, so they need no real network and have predictable timestamps                                                                              |
| 2026-11-01 | Default timeout is 10 seconds, implemented with `AbortSignal.timeout`                                                                                        | Matches the acceptance criteria; a hanging site is reported as down instead of blocking the check                                                               |
| 2026-11-01 | Redirects are followed by `fetch`, and only the status and response time are used, not the body                                                              | The story needs the final status and timing only; avoids downloading page content                                                                               |
| 2026-11-01 | A failed check stores the error message text                                                                                                                 | Shows the user and the history why a check failed                                                                                                               |
| 2026-11-01 | The status view is a command line tool (`npm start -- <url> ...`) for now                                                                                    | Storage does not exist yet; a CLI makes the story demonstrable without a server or UI                                                                           |
| 2026-11-01 | One output line per URL with status, URL, HTTP code and response time or error, and the check time                                                           | Everything the story asks for fits on one line and is easy to read                                                                                              |
| 2026-11-01 | Invalid input and a missing argument set the exit code to 1                                                                                                  | Scripts and the pipeline can detect a failed run                                                                                                                |
| 2026-11-01 | `formatResult` is a pure function, separate from the command line code                                                                                       | It can be unit tested; the entry point stays thin wiring                                                                                                        |
| 2026-11-01 | Check results are stored in SQLite, using Node's built-in `node:sqlite` module                                                                               | Results survive restarts and can be queried for history and uptime; no extra package or native build, which keeps Docker and deployment simple                  |
| 2026-11-01 | Storage is accessed through a `ResultStorage` interface with async methods                                                                                   | Callers do not depend on the database; tests can use an in-memory database                                                                                      |
| 2026-11-01 | History is returned newest first                                                                                                                             | Matches the story's requirement for the history view                                                                                                            |
| 2026-11-01 | Minimum Node version raised from 22 to 24                                                                                                                    | `node:sqlite` is a release candidate without a warning in Node 24; CI already runs Node 24                                                                      |
| 2026-11-01 | One table with one row per check result; columns that exist for only one result shape are nullable                                                           | A responded result has no error and a failed one has no HTTP code or response time; one table keeps queries simple                                              |
| 2026-11-01 | Stored rows are checked at runtime and converted back to `CheckResult`; an unknown outcome throws                                                            | A row the code did not write should fail loudly instead of becoming a wrong result                                                                              |
| 2026-11-01 | Storage tests use an in-memory database; one test uses a temporary file                                                                                      | Tests stay fast and isolated; the file test proves that results survive a restart                                                                               |
| 2026-11-01 | `tsconfig.json` covers `src` and `tests`; `tsconfig.build.json` builds only `src`                                                                            | Tests are type checked in the editor and in CI without ending up in `dist/`                                                                                     |
| 2026-11-02 | The check interval is set with `CHECK_INTERVAL_SECONDS` (whole seconds above 0, default 300); an invalid value stops the program at startup                  | Matches the 5 minute default of the story; a typo in the configuration should fail loudly instead of silently using a wrong interval                            |
| 2026-11-02 | The database file is set with `DATABASE_PATH` (default `isitdown.db`) and `*.db` files are ignored by git                                                    | The path can change for deployment; stored data never ends up in the repository                                                                                 |
| 2026-11-02 | The first round of checks runs immediately at startup, then every interval                                                                                   | The user does not wait a full interval for the first result                                                                                                     |
| 2026-11-02 | A new round is skipped while the previous one is still running                                                                                               | Slow checks cannot pile up                                                                                                                                      |
| 2026-11-02 | A failing check or save is reported and does not stop the other URLs or the scheduler                                                                        | One broken site or a storage error must not stop the monitoring                                                                                                 |
| 2026-11-02 | The scheduler takes the check, the storage and the error handler as options; tests use fake timers and an in-memory storage                                  | Tests run instantly without the network or a database file                                                                                                      |
| 2026-11-02 | Ctrl+C stops the scheduler and closes the database                                                                                                           | The program shuts down cleanly                                                                                                                                  |
| 2026-11-02 | Uptime is the share of `up` results among the results in the period, as a percentage rounded to one decimal                                                  | Simple and easy to explain; one decimal keeps the view readable (66.7 instead of 66.66666666666667)                                                             |
| 2026-11-02 | Uptime counts checks, not elapsed time; times when the monitor was not running are not counted as downtime                                                   | The monitor can only know what it measured; claiming downtime for unmeasured time would be wrong                                                                |
| 2026-11-02 | Uptime is `null` when no result falls in the period                                                                                                          | Nothing was measured, so 0 and 100 would both be misleading                                                                                                     |
| 2026-11-02 | The period includes both ends (from `now - period` up to `now`); results after `now` are ignored                                                             | A result exactly at the start counts, and a result with a future timestamp cannot distort the figure                                                            |
| 2026-11-02 | A failed check counts as down                                                                                                                                | A failed check always has the status down, so it needs no special case                                                                                          |
| 2026-11-02 | `calculateUptime` is a pure function that receives the results, the current time and the period                                                              | It needs no database or clock, so tests are instant and predictable                                                                                             |
| 2026-11-02 | The history is served by a small HTTP server using Node's built-in `http` module, without a framework                                                        | No extra dependency, which keeps the deployment simple; two routes do not need a framework                                                                      |
| 2026-11-02 | `GET /api/history?url=...&period=...` returns the report as JSON; `GET /` serves one HTML page                                                               | The API can be tested and reused; the page makes the history visible to a user                                                                                  |
| 2026-11-02 | Selectable periods are a fixed list (`1h`, `24h`, `7d`) with `24h` as the default; any other value is rejected                                               | No free text to parse, and unknown values get a clear 400 error                                                                                                 |
| 2026-11-02 | The `url` parameter is normalized with `validateUrl` before the lookup                                                                                       | Results are stored under the normalized address, so `https://example.com` finds `https://example.com/`                                                          |
| 2026-11-02 | Errors inside a request give a generic 500 response; the error text is never sent to the client                                                              | Internal details such as paths or database messages must not leak                                                                                               |
| 2026-11-02 | The page shows every value with `textContent`, never as HTML                                                                                                 | Addresses and error messages come from checked websites and must be treated as untrusted text                                                                   |
| 2026-11-02 | The server port is set with `PORT` (whole number from 1 to 65535, default 3000); an invalid value stops the program at startup                               | Same approach as the check interval; a deployment can choose its port                                                                                           |
| 2026-11-02 | The monitor and the history server run in one process and share one storage                                                                                  | One command starts everything, and the page shows what the checks just saved                                                                                    |
| 2026-11-02 | A server startup error such as a port already in use is reported in one line and shuts the program down cleanly                                              | A clear message is more useful than a stack trace                                                                                                               |
| 2026-11-02 | The history page is one HTML string in `src/page.ts`, in a dark theme with the Ubuntu Mono font loaded from Google Fonts                                     | No build step or static files; the font is a visual choice only, and the page falls back to the system monospace font                                           |
| 2026-11-02 | The page shows times in the viewer's local time; the API returns ISO 8601 strings                                                                            | Local time is easier to read, and the API stays unambiguous                                                                                                     |
| 2026-11-02 | The integration test runs the real checker, a real SQLite storage (in memory) and the real history server together                                           | It proves that the parts work together, which unit tests with fakes cannot show                                                                                 |
| 2026-11-02 | The integration test checks a local target server with the routes `/ok`, `/error`, `/redirect` and `/slow`, on a free port                                   | The test needs no internet access, and every answer is predictable                                                                                              |
| 2026-11-02 | The route `/slow` never answers, and the integration test uses a 300 ms timeout                                                                              | A hanging website is tested without waiting for the 10 second default                                                                                           |
| 2026-11-02 | `npm run test` runs the unit tests and skips `tests/integration`; `npm run test:integration` runs only the integration test, each with its own Vitest config | Fast feedback from the unit tests, and the integration test can run as its own job                                                                              |
| 2026-11-02 | The integration test runs as a separate job in the CI workflow, in parallel to `build-and-test`                                                              | It shows up as its own check, and a failure in one job does not hide the other                                                                                  |
| 2026-11-02 | The application is deployed as a Docker container to a Linux server over SSH                                                                                 | The pipeline can set up the whole runtime (Docker, data folder, environment file), which fits the deployment requirements; the same image is the build artifact |
| 2026-11-02 | The server is an Oracle Cloud Always Free VM (VM.Standard.E2.1.Micro, Ubuntu 24.04, Zurich region)                                                           | A free server with no time limit and no region restriction; the AMD shape needs no ARM image                                                                    |
| 2026-11-02 | The AMD shape is used instead of the ARM shape                                                                                                               | The Docker image only needs an `x86_64` build, which keeps the pipeline simple                                                                                  |
| 2026-11-02 | A separate SSH key pair is used for deployment, without a passphrase                                                                                         | The pipeline cannot type a passphrase, and a key used only for this purpose can be replaced without affecting anything else                                     |
| 2026-11-02 | The private key and the server address are stored as GitHub secrets, never in the repository                                                                 | The repository is public                                                                                                                                        |
| 2026-11-02 | The deployment sets up a swap file on the server                                                                                                             | The server has about 1 GB of memory and no swap, and installing or running containers could run out of memory                                                   |
| 2026-11-02 | The build artifact is a Docker image, published to the GitHub container registry (`ghcr.io`)                                                                 | The same image is what gets deployed to the server, so the artifact and the deployment are one thing                                                            |
| 2026-11-02 | The image is built in two stages and contains only the compiled code                                                                                         | The final image stays small, which matters on a server with 1 GB of memory                                                                                      |
| 2026-11-02 | The container runs as a non-root user, and the database lives in `/data`                                                                                     | A compromised app has fewer rights, and a mounted folder keeps the results between versions                                                                     |
| 2026-11-02 | A release is created by pushing a version tag (`v*.*.*`)                                                                                                     | Only a deliberate action publishes an image; normal pushes and pull requests never do                                                                           |
| 2026-11-02 | The image is tagged with the version (`0.1.0`, `0.1`) and the commit (`sha-...`), and labelled with its source repository and commit                         | Any running image can be traced back to the exact source it was built from                                                                                      |
| 2026-11-02 | The release workflow logs in with the built-in `GITHUB_TOKEN`                                                                                                | No extra password or secret is needed to publish                                                                                                                |
| 2026-11-02 | The container image is public                                                                                                                                | The server pulls it without a login; it contains only the compiled app and no secrets                                                                           |
| 2026-11-02 | Deployments use the version tag of the image, not `latest`                                                                                                   | A fixed tag shows which version runs and allows a rollback to an earlier one                                                                                    |
| 2026-11-02 | A failed release is fixed with a new version tag, not by moving the old tag                                                                                  | The history stays honest, and a tag that CI already ran for is not changed                                                                                      |
| 2026-11-02 | The deployment is a second job in the release workflow and runs after the image is published                                                                 | A failed build means no deployment, and the server only pulls an image that exists                                                                              |
| 2026-11-02 | A version tag triggers the deployment                                                                                                                        | The same deliberate action that publishes the image also deploys it                                                                                             |
| 2026-11-02 | The deploy job uses the `production` environment                                                                                                             | GitHub records every deployment, which shows what ran and when                                                                                                  |
| 2026-11-02 | The server is set up by a script (`deploy/remote-deploy.sh`) that the workflow sends over SSH; every step checks first whether it is needed                  | The runtime setup is part of the pipeline, and running the script again is safe                                                                                 |
| 2026-11-02 | Docker is installed from Ubuntu's own package (`docker.io`)                                                                                                  | No third-party repository or key has to be added to the server                                                                                                  |
| 2026-11-02 | The container is started with `--restart unless-stopped` and a named volume for the data                                                                     | The app comes back after a reboot, and the results survive new versions                                                                                         |
| 2026-11-02 | The workflow pins the server's host key (a secret) and connects with strict host key checking                                                                | A connection to a different server fails instead of being trusted                                                                                               |
| 2026-11-02 | The version and the list of URLs are checked against a strict pattern before they reach the server command                                                   | They end up inside a command line, so only plain characters are allowed, which rules out command injection                                                      |
| 2026-11-02 | Secrets reach the steps as environment variables, and only the publishing job may write packages                                                             | Secrets are not pasted into script text, and each job has only the rights it needs                                                                              |
| 2026-11-02 | The websites to monitor are a repository variable, `MONITOR_URLS`, not a secret                                                                              | The list is not sensitive, and a variable can be changed without touching the code                                                                              |
| 2026-11-02 | Two deployments cannot run at the same time                                                                                                                  | They would compete for the same container                                                                                                                       |
| 2026-11-02 | Port 3000 is opened to the internet in the cloud network rules                                                                                               | The history page has to be reachable; it has no login and shows only public uptime data                                                                         |
| 2026-11-02 | The application has a `/health` endpoint that answers `{"status":"ok"}`                                                                                      | A deployment needs a simple, stable answer that shows the application is running                                                                                |
| 2026-11-02 | The health endpoint checks only that the process runs and the server answers, not the database or the monitored websites                                     | A deployment check that depends on external websites would fail for reasons that have nothing to do with the deployment                                         |
| 2026-11-02 | The deploy job calls `/health` from the GitHub runner over the internet                                                                                      | It tests the whole path a user takes, including the open port in the cloud network rules                                                                        |
| 2026-11-02 | The check retries 12 times, 5 seconds apart, and fails the deployment if the answer is not healthy                                                           | The container needs a moment to start, and a deployment that does not become healthy must not look successful                                                   |
| 2026-11-02 | The check accepts only an answer that contains `"status":"ok"`                                                                                               | Another page on the same port must not count as a healthy application                                                                                           |
| 2026-11-02 | After a failed check, the job prints the last lines of the container log                                                                                     | A failed deployment comes with a clue about the cause                                                                                                           |
